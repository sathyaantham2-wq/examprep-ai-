# Data dictionary (F111)

40 tables, grouped by domain. This is generated from the real schema (`src/db/types.ts`, itself
generated by `kysely-codegen` from the live DB — never hand-edited) plus one line of purpose per
table written from how each is actually used in `src/lib/**` / `src/db/repositories/**`. Tab 04 of
the plan spreadsheet sketched 26 tables at scoping time; the real count grew to 40 as auth
(better-auth's own tables), privacy (consents/deletion_log), and ops (generation batches) tables
were added during the build — that's expected drift, not spec violation.

Full column-level detail lives in the migration that created the table (`src/db/migrations/NNNN_*.ts`)
and the generated type (`src/db/types.ts`) — this doc is the map, not a restatement of every column.

## Household, auth & consent

| Table | Purpose |
|---|---|
| `households` | The billing/ownership unit. One parent's family. `owner_user_id` points at the parent who created it. |
| `users` | People who can sign in — `role` is `parent` \| `student` \| `admin`, set once at creation (F007); scoped to one `household_id`. |
| `students` | A child profile within a household. Not every student has a `user_id` yet (self-service student login is F112, not built) — parents act on a student's behalf via the household scope until then. |
| `consents` | F095/DPDP: one row per consent grant, append-only. `withdrawn_at` records withdrawal; the row is never deleted. A student cannot exist without a matching consent row (enforced transactionally at creation). |
| `accounts` | better-auth's credential store (password hashes) — one row per login method per user. |
| `sessions` | better-auth's session table — the source of truth behind the `requireUser`/`requireRole` cookie check. |
| `verifications` | better-auth's email-verification token store. |

## Syllabus & content scope

| Table | Purpose |
|---|---|
| `subjects` | `(board, class, code)` — e.g. CBSE / 7 / MATH. Never hardcode "Class 7"; this table is why. |
| `sources` | A textbook edition (e.g. NCERT *Ganita Prakash* Part I) — `file_ref` for the source PDF. |
| `chapters` | Identity is `(source_id, part, chapter_no)` **not** `chapter_no` alone — see `ADR-0001-chapter-identity.md`. Two Chapter 3s exist across the two parts. |
| `chapter_scope` | Line items citing exactly what a chapter covers (`item_text`, `page_ref`) — the thing every concept must trace back to (invariant 5). |
| `concepts` | The atomic unit questions are generated against. Carries `board`/`class` directly (never inferred), `target_question_count` (F113's per-concept depth config), and `code` (`C7M-3.2` convention). |
| `concept_prereqs` | Directed prerequisite edges between concepts (used by remediation sequencing). |
| `concept_remediation_content` | AI-generated refresher text + worked examples per concept (F066), cached so the same concept isn't re-generated per student. |

## Question bank

| Table | Purpose |
|---|---|
| `questions` | Draft → Approved → Retired (`status`), never hard-deleted (invariant 4). `origin` distinguishes `manual` vs `ai_generated` (F025). `text_hash` de-duplicates near-identical generated questions. |
| `question_options` | MCQ options, one row per option, `is_correct` flag — never sent to a student-role response. |
| `question_step_marks` | Step-wise mark breakdown for multi-step questions — what the AI evaluator justifies its proposed marks against. |
| `question_usage` | Which paper served which question to which student, and whether they got it right — feeds "don't repeat a recently-served question" selection logic. |

## Papers

| Table | Purpose |
|---|---|
| `blueprints` | A reusable paper template: `sections`, `bloom_targets`, `choice_rules`, versioned (`version`) so a paper can pin the exact blueprint version it was generated from. |
| `papers` | One generated paper instance — `chapter_ids` (the in-scope set), `weighting` (F119's 40% weak-concept weighting actually applied), `shortfalls` (F032 — printed, never hidden, when the bank couldn't fill a slot). |
| `paper_questions` | The ordered, sectioned set of questions actually placed on one paper. |

## Attempts & evaluation

| Table | Purpose |
|---|---|
| `attempts` | One student's sitting of one paper — `mode` (`online` \| `uploaded`), `status`. |
| `attempt_answers` | One answer per paper question — `source` (typed vs OCR'd), `ocr_confidence` when scanned. |
| `uploads` | A scanned-answer-sheet file reference for `uploaded`-mode attempts (M10 — not yet built; table exists, upload/OCR pipeline is skipped pending storage credentials). |
| `evaluations` | One per attempt. `evaluated_by` (`ai` \| `human`), `confirmed_at` — **the mastery/dashboard code only ever reads evaluations where `confirmed_at is not null`**; an AI proposal alone changes nothing (hard rule in `CLAUDE.md`). `delivery_gap` is the "knew it but lost marks anyway" metric this whole product exists to surface. |
| `evaluation_items` | Per-question mark + `knowledge_known` / `error_type` classification, `ai_marks` (proposal) vs `marks_awarded` (confirmed, possibly human-overridden via `overridden_by`). |

## Tracking, mastery & habits

| Table | Purpose |
|---|---|
| `concept_mastery` | Append-only ledger — one row per (student, concept, evaluation). Ordered by `date desc, created_at desc` (the `created_at` tiebreaker exists because `date` alone can't disambiguate two same-day evaluations — F074's ordering fix). |
| `concept_status` | The current rollup per (student, concept): `status` (Weak/Priority/Maintenance/etc, F063's escalation state machine), `trend`, `next_retest_at`. |
| `patterns` | Named delivery-habit patterns (e.g. "stops mid-working on 4+ mark questions") the evaluator can flag. |
| `pattern_hits` | One row per detected pattern occurrence, linked to the `evaluation_item` it was seen in. |
| `habits` | The habit taxonomy (`target_behaviour`) patterns roll up into. |
| `habit_observations` | Per-evaluation habit rating — feeds the "delivery habit, not knowledge gap" diagnosis. |
| `remediation_tasks` | A generated drill for a weak concept (F066/F067) — `question_ids`, `status`, `due_at`. |
| `study_plans` | A week's worth of scheduled remediation/practice (`days` JSON), `status`. |

## Generation ops

| Table | Purpose |
|---|---|
| `generation_batches` | A bulk top-up job (F116) — `cost_cap_inr` / `cost_spent_inr` enforce the spend ceiling; `status` tracks the whole batch. |
| `generation_batch_items` | One (concept × bloom × difficulty) cell within a batch, with its own `target_count`/`generated_count`/`status` — resumable per-cell, not all-or-nothing. |
| `ai_jobs` | Generic AI call ledger — `feature`, `model`, `tokens_in`/`tokens_out`, `cost_inr`, `latency_ms`. The audit trail for "what did AI usage actually cost this household." |

## Privacy, audit & notifications

| Table | Purpose |
|---|---|
| `audit_log` | Append-only trail of sensitive writes (F099) — evaluation confirmations, consent withdrawals, evaluation-item overrides. Household-scoped, readable via `GET /api/audit-log`. |
| `deletion_log` | F098's DPDP right-to-erasure trail. Deliberately **not** an FK to `households` — if it were, `ON DELETE CASCADE` would erase the very audit row proving the erasure happened. This is the one place in the schema where a household-scoped row survives its household's deletion, on purpose. |
| `notifications` | Per-user notification queue (`channel`, `template`, `payload`, `sent_at`/`read_at`) — delivery (email/WhatsApp) is M16, not yet built; rows are written but not yet dispatched anywhere. |
